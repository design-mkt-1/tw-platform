## Wave B — the fixes

### B1 — the dead menu links

> All eleven menu links were dead because UrlStateBridge called window.history.replaceState(null,
> ...): Next patches replaceState and dispatches ACTION_RESTORE for any call whose state is not its
> own, and Next's queue marks the pending ACTION_NAVIGATE as discarded — so closePanel's URL write
> killed the navigation the same click had just started, which is why no pushState was ever issued.
> Settled by experiment, not by reading: leaving onClick={closePanel} in place (so the Link still
> unmounts) but disabling only the bridge's write effect made SPORT navigate and push /sport, clearing
> the unmount hypothesis; the fix is to pass window.history.state instead of null, which takes Next's
> own __NA short-circuit, plus a path comparison across bridge mounts so a route change closes a panel
> rather than re-reading panel=menu at the destination. Verified in Chrome at 390x840: all eleven rows
> land on their href with the panel closed (dead ones on the app's not-found page), CASINO-while-on-/
> closes the menu and restores focus to the opener, a bottom-nav tab with the menu open leaves no panel
> and no panel= param; tsc, eslint and 147 tests clean, axe shows no new rule id.

## Five things the coordinator got wrong, and how they were caught

A handover that records only what turned out right teaches nothing. Each of these was stated with
confidence in a worker brief or to the owner, and each was refuted by measurement.

**1. "It is not `UrlStateBridge`."** The coordinator probed `window.history.state` before and after
a panel toggle, saw `__NA` and `__PRIVATE_NEXTJS_INTERNALS_TREE` intact, and told the owner the
bridge was cleared. It was the bridge. The state survived *because Next's own patch had restored
it* — the probe photographed the repair and read it as proof nothing had broken. What the probe
should have measured was the navigation, not the state object.

**2. "`SportNavRow` is rendered outside its plate."** W2 measured that it is inside. The defect was
two nested plates with `pt-3` applied three times, not a child escaping its parent.

**3. "The sport filter pills all read `310`, a recorded design placeholder — do not file them."**
Carried from the inventory into two briefs. The build had already varied them to `310 / 84 / 46`
before this session. Nothing broke, but the instruction was stale.

**4. "Count elements whose computed `filter` contains `drop-shadow`."** Given to W2 as the way to
prove the doubled shadow. `shadow-container` is a `box-shadow`; the count returns zero and proves
nothing. W2 used a pixel comparison instead and said so.

**5. "Read `.rounded-full` to find the mode track."** That selector self-matches the Прематч
button, which also carries `rounded-full`, so the check reads 88 rather than 84. The real track is
`.bg-track`. B2 ran the brief verbatim, got the wrong number, found out why, and reported both.

The pattern in all five: a claim that was *plausible from reading* and wrong *on measurement*. The
briefs that survived contact were the ones that named a node id and a file line for every number.

## What the sweep could not do

Named rather than glossed, because an unmeasured check that reads as passed is worse than a gap.

- **`resize_window` reports success and does nothing on a maximized window.** W4 saw `clientWidth`
  stay at 2537 across two attempts, so 200% zoom was measured as its layout-viewport equivalent in
  Playwright rather than through Chrome's own zoom UI.
- **`chrome://settings/appearance` was unreachable**, so the text-only-zoom finding (WCAG 1.4.4) is
  reasoned from `tailwind.config.ts:173-195` being entirely px, **not observed in a browser**.
- **`env(safe-area-inset-*)` reads zero in desktop Chrome** and device emulation does not supply
  insets, so the notch region was checked by pairing the five call sites in code, not by looking.
- **The `SearchOverlay` truncate spans could not be reached without a query**, so B4 left them
  unmeasured rather than assuming they were safe.
- **The Figma deep links in `/dev/screens` could not be opened from this machine.** The Chrome
  profile is signed in as `design1@marketing-solutions.ro`, which does not have access to file
  `s2CqwGqe0O0FcALhBNlTRe`; the MCP server does. The URL form was confirmed correct — Figma
  resolved it and named the file *Top-Win* on its request-access screen — but the links themselves
  are unverified from here and will work for whoever owns the design.
